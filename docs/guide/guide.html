2. How SPG works (what a tester must know)

CMS and API

The CMS (stagecms) is a React app. Every screen calls the SPG API (stageapi …/v1). Testing the API tests the same rules the CMS uses.

One session per account

A new login ends the previous one. If Postman, the CMS and a teammate share an account, they log each other out with "Invalid Token!". The automation logs in once and shares that session.

How photos work

The CMS uploads the picture straight to cloud storage (S3, via a Cognito identity), then saves only the file key in fields like profilePhoto or entityLogo. The API never receives the image itself.

Entity context

Entity screens send the header x-effective-role: entityPrincipalAdmin – the same as "Login on behalf". Client, alert-group and emergency calls need it.

Updates need the full record

PATCH requests must send the whole object (same shape as create). Partial bodies are rejected – and on "my profile" they erase fields (SPG-BUG-11).

Emergencies

Start = POST /admin/emergency. Mark as safe = PATCH /admin/emergency/{id} with {} – it works. Posting a response comment crashes staging (SPG-BUG-24) – never automate it.

Building blocks

PieceJob
apiCalls the SPG API with the shared session; logs in again if another login ended it.
worldRemembers IDs and request bodies between the steps of one scenario.
cleanupDeletes everything the scenario created – even when it fails. QA entities are left disabled (no delete endpoint).
CMS sign-inUI tests put the API token into the browser (serviceToken) instead of typing the password – a second login would log out the API tests.
redact()Removes passwords, hashes and tokens from every failure message and report.

4. Run it on Linux

One command for everything

./run.sh setup        # once: Node packages + Chromium (no sudo needed)
./run.sh smoke        # 5 quick scenarios
./run.sh test         # everything – API + CMS (~5 min) + sprint report
./run.sh postman      # Postman collection with newman (~2 min)
./run.sh report       # open the HTML report
./run.sh skills       # install the AI skills for Claude Code / OpenClaude

Run it from the package folder (where run.sh is). In your private copy the password is already in spg-qa-automation/.env.

Or directly inside the project

CI (GitHub Actions)

Pull requests run @smoke, a nightly job runs @regression, results go to Slack and reports are kept for 30 days. Add the password as a repository secret (SPG_ADMIN_PASSWORD) and the URLs as variables. GitLab / Bitbucket: run the same four commands.

Postman (manual / API QA)

  1. Import the collection and environment from SPG_API_QA_Report_…/postman/.
  2. Set adminPassword as Current value; set Postman's working directory to the postman/ folder (photo upload).
  3. Run the collection in order. Folders 00–13, 97, 99 should be green; folder 98 (known bugs) is red until fixed.

AI rules for the team

  1. AI drafts, people approve (QA Lead review stays).
  2. Verify everything: bddgen, type check and a real run before merging.
  3. Confirmed vs suspected – never log a suspicion as a bug.
  4. No secrets in prompts or output.
  5. Never let AI run actions that harm shared environments.
  6. Security findings stay high-level and on restricted pages.

Sprint checklist (QA guide)

  1. Sprint planning: generate and review test cases for the next two sprints (RTM + Gherkin).
  2. During the sprint: automate approved scenarios; tag @wip until the feature is deployed.
  3. Every merge: CI runs @smoke; a failing pipeline blocks the merge.
  4. Regression sprint: npm run test:regression + Postman collection.
  5. Release: sprint automation report + release report (qa-docs-writer), bugs linked in Jira.
  6. Retro: review known bugs that turned green and flaky timing results.
